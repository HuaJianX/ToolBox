# 二、技术选型与项目结构

## 1. 桌面框架：选 .NET WPF，不选 Tauri

先说结论：**头像里那些转换活儿全是「调外部命令行 + 调原生库」，桌面框架本身只是个壳。**

| | .NET 10 WPF（本方案） | Tauri 2 |
|---|---|---|
| 需要装什么才能构建 | 只要 .NET SDK | Rust 工具链 + Node + MSVC 生成工具，四样 |
| 界面语言 | XAML（C# 同一个工程） | HTML/CSS/JS 前端 + Rust 后端 + IPC 两层 |
| 发布目录体积 | 自包含 **158 MB**；依赖 .NET 运行时 **26.5 MB**（本机实测） | ≈ 10 MB（靠系统自带 WebView2） |
| 启动速度 | 约 0.3–0.6 秒 | 约 0.5–1 秒（要先拉起 WebView2） |
| 调外部程序 / 文件对话框 / 拖拽 | 一行的事（`Process`、`OpenFileDialog`、`AllowDrop`） | 每个都要写 IPC 命令 + 前端绑定 |
| 本项目的实际收益 | 转换逻辑 100% 是 C# 调进程，没有一行前端逻辑 | 多一层 IPC 序列化，对这个程序没有任何好处 |

**所以选 WPF。** Tauri 唯一真正的优势是安装包小一半，代价是多三套工具链和一层 IPC。
这个程序的界面就是「几个大按钮 + 一个进度条」，用 Web 技术画不出额外价值。

> 如果哪天非要压体积：把 `dotnet publish` 的 `SelfContained` 去掉（改成依赖
> 「.NET 10 桌面运行时」），发布目录立刻从 **158 MB** 掉到 **26.5 MB**，启动速度不变。
> 代价是用户机器上得先有运行时 —— 安装脚本里可以静默装。
> 剩下那 26.5 MB 里有 23.1 MB 是 `Magick.Native-Q16-x64.dll`（图片功能的家当），压不动。

## 2. 转换引擎分工

一个格式交给谁，全写在 `ConversionService.cs` 和 `FormatCatalog.cs` 里，改一处全局生效。

| 功能 | 优先用谁 | 退而用谁 | 安装包里带不带 |
|---|---|---|---|
| 图片 JPG/PNG/WEBP/BMP/GIF/TIFF 互转 | **Magick.NET**（ImageMagick 的 .NET 封装） | — | ✅ 编译进程序，零外部依赖 |
| 图片 **HEIC 读取**（→ JPG/PNG/WEBP） | 同上（libheif 解码器） | — | ✅ |
| 图片 **写出 HEIC** | ❌ 做不到，见下文 | — | — |
| 音频 MP3/WAV/FLAC/M4A 互转 | 本机 **FFmpeg** | 下载的 FFmpeg | ✅ `tools/ffmpeg/bin`（41 MB） |
| 视频 MP4/MKV/AVI/MOV 互转 | 同上 | 同上 | ✅ |
| 视频提取音频 | 同上（`-vn`） | 同上 | ✅ |
| Word/Excel/PPT/TXT → PDF | 本机 **LibreOffice**（headless） | 本机 **Microsoft Office**（COM） | ❌ 都不用带，用本机现成的 |
| Markdown → PDF | 本机 **Pandoc** 排版 → 上面任一引擎 | 当纯文本交给 Word 排 | ✅ 可选（40 MB） |
| PDF → 图片 | 本机 **Poppler**（`pdftoppm`） | **Windows 自带** `Windows.Data.Pdf` | ✅ 内置的能力不用带 |
| PDF → 纯文本 | 本机 **Poppler**（`pdftotext`） | LibreOffice | ✅ `tools/poppler`（1.6 MB） |
| PDF → Word | ❌ 只有 LibreOffice 做得到 | — | ❌ 需要单独装 |

**核心思路：先看本机有什么，再决定要不要下载。**
每个功能都有「本机现成的 → 系统自带的 → 才下载」这条链，
所以在一台装了 Office 和 B 站客户端的机器上，五个大按钮全部可用、一个字节都不用下。

**设计取舍：为什么 LibreOffice 不塞进安装包？**
它本来就是 350 MB 的独立办公软件，用户多半已经装了。程序启动时就找
`C:\Program Files\LibreOffice\program\soffice.exe`，找到就能用，找不到就给一句人话提示。
这样就省掉了为了文档功能而去背 350 MB。图片功能则完全不依赖任何外部组件 ——
Magick.NET 的原生库跟着 exe 走，**装完就能用**。

**为什么 Markdown 要绕道 docx？**
Pandoc 直接出 PDF 需要 LaTeX（TeX Live / MiKTeX），那是一个多 G 的东西，跟「体积小」直接冲突。
而 LibreOffice 反正已经在用，所以走 Markdown → docx → PDF。没装 Pandoc 时再降级成
「把 .md 当纯文本交给 LibreOffice」—— 标题符号不排版，但内容一个不少。

## 4. 一次转换是怎么走完的

```
用户点「开始转换」
   │
   ▼
MainViewModel.StartAsync()
   │  按文件列表循环（批量就是简单的 for，一个失败不影响下一个）
   │  每个文件 new 一个 ConversionJob + IProgress + CancellationToken
   ▼
ConversionService.ConvertAsync()
   │  ① 文件还在不在？  ② 输出目录建好没？  ③ 磁盘空间够不够？（按源文件 2 倍估）
   │  异常在这里统一被 FriendlyError 翻译成中文
   ▼
按 CategoryKind 分派
   ├── Image    → ImageConverter        → Magick.NET（进程内，无外部依赖）
   ├── Audio    → FfmpegConverter       → ffmpeg.exe
   ├── Video    → FfmpegConverter       → ffmpeg.exe
   ├── Document → md? → PandocConverter → pandoc.exe → soffice.exe
   │             其它 → LibreOfficeConverter → soffice.exe
   └── Pdf      → png/jpg? → PdfConverter.ToImages   → pdftoppm.exe
                  txt?     → PdfConverter.ToText      → pdftotext.exe
                  docx?    → PdfConverter.ToWord      → soffice.exe
   ▼
ConversionOutcome（成功/失败 + 人话消息 + 产出路径）
   ▼
界面：全绿 → 「🎉 转换好了」；有失败 → 红字说清楚第几个文件、为什么
```

## 5. 踩过的坑（都是实测出来的，不是猜的）

**① WPF 的隐式 using 里没有 `System.IO`**
.NET 10 的 WPF 项目，`ImplicitUsings` 只给 5 个命名空间：
`System`、`System.Collections.Generic`、`System.Linq`、`System.Threading`、`System.Threading.Tasks`。
没有 `System.IO`，所以 `File`、`Path`、`Directory` 全都找不到。已在 csproj 里补：

```xml
<Using Include="System.IO" />
```

**② HEIC「互转」做不到一半 —— 这是最重要的实测结论**
实测 `Magick.NET-Q16-x64 14.17.1`：

```
SupportedFormats.Count = 284
Heic  : read=True   write=False   module=Heic
Avif  : read=True   write=True    module=Heic
Jpg/Png/WebP/Bmp/Tiff/Gif : read=True write=True
```

用两个真实 HEIC 样张验证过解码确实通（1280×854、1440×960 → JPG/PNG/WEBP 全部成功）。
**但反过来「转成 HEIC」会报 `no encode delegate for this image format 'HEIC'`** ——
HEIC 编码依赖 x265，因为专利授权原因不随包分发。

所以程序里做的事：**HEIC 只作为来源格式（iPhone 照片转 JPG 完全没问题），
不作为目标格式**，格式列表里干脆不放这个按钮。如果是别处传进来的 HEIC 目标，
直接返回一句人话：「HEIC 图片只能读、不能生成……建议转成 JPG 或 PNG」，
而不是把底层的英文报错甩给用户。

> 真要支持写 HEIC，得另外塞一个带 x265 的编码器，会引入专利授权问题，不建议在第一版做。

**③ LibreOffice 转换失败也返回退出码 0**
`soffice --convert-to` 出错了照样 `exit 0`，光看退出码会误判成功。
唯一可信的判断是**产物文件到底有没有生成**，所以代码里是查 `File.Exists` 而不是查退出码。

**④ LibreOffice 单实例锁**
用户自己开着 LibreOffice 时，命令行转换会抢用户配置目录的锁然后直接失败。
解决办法是每次转换都指定一个独立的配置目录：

```
-env:UserInstallation=file:///C:/Temp/.../profile
```

顺带好处：可以同时转多个文件，互不干扰。

**⑤ FFmpeg 的进度要这么读**
不要解析给人看的 stderr（格式会变）。正确做法是
`-progress pipe:1` 让 ffmpeg 往 stdout 打机器可读的进度，再解析 `out_time=00:00:05.123456`；
总时长先用 `ffprobe -show_entries format=duration` 问出来。
**算不出来的时候（比如直播流）就显示滚动进度条，不假装百分比。**

**⑥ 取消要杀整棵进程树**
`Process.Kill(entireProcessTree: true)`。不然取消后 ffmpeg 的子进程还在后台吃 CPU。
另外 `WaitForExitAsync` 故意不传 token：先杀进程、等它真的退出、拿到退出码，
**最后**才抛 `OperationCanceledException`，这样临时目录才清理得干净。

**⑦ 参数用 `ArgumentList` 而不是拼字符串**
`"中年妇女 的照片.jpg"` 这种带空格和中文的文件名，拼引号很容易翻车。
`ProcessStartInfo.ArgumentList` 由运行时负责转义，永远不会错。

**⑧ 中文 .ps1 必须存成带 BOM 的 UTF-8**
`tools\get-tools.ps1` 一开始没带 BOM，在中文 Windows 上被按 GBK 读取，
中文全变乱码、字符串引号都配不上，PowerShell 直接语法错误。加 UTF-8 BOM 后正常。

## 6. 实测验证情况

`tests\ToolBox.SmokeTest` 是一个不开界面、直接调转换引擎的自检程序。
它有个关键设计：**装了外部组件就做真实转换，没装就退回去验证「缺组件时的中文提示」**，
所以在任何机器上跑都不会出现「假绿」。

当前结果：**通过 13 项，失败 0 项**。

| 验证内容 | 结果 |
|---|---|
| PNG → JPG / PNG / WEBP / BMP / TIFF | ✅ 5 种全部产出文件 |
| **HEIC → JPG / PNG / WEBP**（真实 1440×960 样张） | ✅ 全部产出文件 |
| 转 HEIC 被拒绝，且提示是人话 | ✅ |
| 坏文件的提示是人话 | ✅ |
| 缺 FFmpeg / LibreOffice / Poppler 时的提示 | ✅ 三条都是人话 |
| 界面能启动、XAML 能加载、无异常 | ✅ 开发版和自包含发布版都实测启动过 |
| 自包含发布体积 | ✅ 实测 158 MB / 258 文件；依赖运行时 26.5 MB / 7 文件 |

### 没能在这台机器上跑真实转换的部分

音视频、文档、PDF 这三条链路的**真实转换**没跑成，原因很实在：
ffmpeg 的 Windows 构建下载包有 106 MB，而这台机器的网络只有 20–50 KB/s
（GitHub 的 release 下载还被直接挡掉了），没能在合理时间内下完。

代码是照着实测可以验证的方式写的，并且自检程序已经准备好：
**在那台机器上跑一次 `tools\get-tools.ps1`，再跑一次自检，这三项会自动变成真实转换测试。**
音视频那一节还会顺手验证 FFmpeg 的进度解析（用 lavfi 合成 2 秒素材，
检查是否收到了百分比进度），这是整份代码里最容易写错的一段。

## 7. 以后要加功能，改哪里

想加「图片转 PDF」这类新格式，最少只要动两个文件：

1. `Services\FormatCatalog.cs` —— 在对应类别的 `Targets` 里加一行 `FormatOption`，
   界面会自动多出一个按钮，**XAML 一个字都不用改**。
2. `Services\ConversionService.cs` —— 在 `ConvertAsync` 的分派里加一个分支，
   指向已有的转换器（或者新写一个 `Converters\XxxConverter.cs`）。

前四个大按钮（图片/文档/PDF/音频/视频）的框架是通用的，将来加「压缩包」「重命名」
「批量改名」之类的工具，只要新加一个 `CategoryKind` 和对应的转换器即可。
